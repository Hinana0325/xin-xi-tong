# QEMU boot verification result — xin-xi-tong bootable image (QEMU virt only)

Harness: `run-boot.sh` + `unpack_bootimg.py` in this directory.
Host: x86_64, 2 vCPU, 7.7 GiB RAM, `qemu-system-aarch64` 8.2.2, TCG
(`-machine virt -cpu cortex-a57 -smp 2 -m 2048 -display none`, serial to
file). Every run used copies in its own `work/` subdirectory; originals
were never written to. GSI zip SHA-256 re-checked during this task:
`a359a50b6eb8e9f63168e928bd14167603225e92cd8605ec86a4bda6591fc13b`.

**Bottom line: Android did NOT boot in any run. No adb, no SurfaceFlinger,
no second-stage services, no desktop. The furthest stage reached in any
run is "kernel executes /init, which terminates immediately without
printing anything". The blocker is in the first-stage ramdisk / init
binary, not in the kernel, the disks, SELinux flags, or the system.img
variant. See SUGGESTIONS.md for the evidence-based next experiments.**

## Runs

### 1. `logs/baseline-01/` — baseline panic reproduction (harness check)

Command: kernel + stock modules-only `initramfs.img`, plain GSI
`system.img`, 150 s reboot loop, then killed.
Result: **23 identical panics, 8,357 lines.** First panic at serial.log
line 337 (`Kernel panic - not syncing: VFS: Unable to mount root fs on
unknown-block(0,0)`). Kernel boots, 3 virtio-blk disks probed
(`stage-scan.txt`: virtio lines 218–222), no `/init` executed.
Conclusion: harness reproduces the previous round exactly; harness itself
works.

### 2. `logs/ramdisk-01/` — A ramdisk, plain GSI system.img (main run)

Command: A kernel + A `ramdisk.cpio.gz`, plain GSI `system.img`,
`-no-reboot`, exited on its own after ~40 s guest time.
Result: **furthest stage = kernel executes /init.**
Evidence (`serial.log`):
- Line 283: `Run /init as init process`
- Lines 284–285: linker warning `failed to find generated linker
  configuration from "/linkerconfig/ld.config.txt"` (twice)
- Line 286: `libc: Fatal signal 6 (SIGABRT), code -1 (SI_QUEUE) in tid 1
  (init), pid 1 (<unknown>)`
- Line 287: `Kernel panic - not syncing: Attempted to kill init!
  exitcode=0x00000100`
- Zero `init:` lines, zero first-stage mount/fstab lines.
  **First-stage mount: NOT REACHED. Second-stage: NOT REACHED.
  SurfaceFlinger: NOT REACHED. adb: NOT REACHED.**
A's own smoke log (`bootable-ramdisk/diag-serial.log`, lines 283–291)
shows the same shape (panic `exitcode=0x00002a00`).

### 3. `logs/diag-sh-01/` — INVALID diagnostic (wrong override, disregard)

Used `init=/system/bin/sh`, which the kernel ignores when an initramfs
`/init` exists; it ran `/init` and aborted identically. Kept for the
record; no conclusion drawn from it.

### 4. `logs/diag-sh-02/` — `rdinit=/system/bin/sh` (decisive diagnostic)

Same kernel + A ramdisk, `rdinit=/system/bin/sh`, 60 s no-progress watchdog.
Result: **toybox `sh` runs.** Line 283: `Run /system/bin/sh as init
process`; same linker warning at 284–285 (non-fatal here); log ends with
`/system/bin/sh: No controlling tty…` and a `# ` prompt, idling until the
watchdog killed QEMU (exit 124 by design).
Conclusion: kernel, initramfs unpack, dynamic linker, and bootstrap
libraries all work. The abort is specific to the `init` binary's early
startup path, not a generic userspace failure.

### 5. `logs/ramdisk-02-selinux-disabled/` — SELinux hypothesis excluded

Same as run 2 but `androidboot.selinux=disabled` instead of `permissive`.
Result: **identical abort**, serial.log lines 283–287 (panic
`exitcode=0x00007f00`). SELinux is not the sole cause; do not re-chase
selinux flags.

### 6. `logs/bundle-01/` — B bundle as packaged (`boot.img` only)

B's `boot.img` unpacks to kernel-only (`ramdisk_size=0`), so no initramfs
init existed. Result: **VFS panic**, line 310, 331 lines. B's bundle as
packaged cannot boot: its ramdisk lives in the separate `ramdisk.img`.

### 7. `logs/bundle-02/` — B bundle (`boot.img` + B `ramdisk.img`)

B's `ramdisk.img` is the stock modules-only initramfs (LZ4 cpio listing
is `lib/modules/**` only, no `/init`, no fstab). Result: **VFS panic**,
line 314, 335 lines. B copied the modules initramfs as the ramdisk; its
`/init` and fstab were never inspected (B's own manifest says so).

### 8. `logs/bundle-03/` — B integrated system.img + A ramdisk (correct combo)

Kernel from B bundle (same SHA as A kernel) + A `ramdisk.cpio.gz` + B
integrated `system.img`. Result: **identical init abort**, lines 283–287
(panic `exitcode=0x00007f00`). The abort is independent of which
system.img variant is attached; it is ramdisk/init-side.

## Blocker (for A)

GSI `init` terminates (SIGABRT, no output) during its earliest startup,
before first-stage mount. Excluded by experiment: generic userspace/linker
failure (sh runs), SELinux flags (disabled aborts identically), missing
libraries (all 17 `DT_NEEDED` libs present with real sizes). The missing
`/linkerconfig/ld.config.txt` (empty `linkerconfig/` dir in the ramdisk
and in `system.img`) is the only userspace diagnostic in the log but is
**not proven** to be the cause (sh survives the same warning). See
`SUGGESTIONS.md` S1–S4 for the ordered next experiments (generate
`ld.config.txt`; find init's abort site; compare with an AOSP-built
first-stage ramdisk; revisit fstab only after init survives).

## Notes / caveats

- B's bundle tested here contains **dummy APKs only** (`manifest.json`:
  `real_apks_verified: false`, Agent APK 359 bytes). A successful boot of
  it would prove pipeline + ramdisk only, not real apps. Separately, the
  parent reported real APKs built in WorkBuddy and fixes backported
  locally to `~/workspace/system-apps/` (unbuilt/unpushed on this VM);
  no real-APK integrated image exists on this VM, and none was
  boot-tested here.
- B's `bundle-sample/` was mid-rebuild at 04:40 UTC (only `.staging/`
  present); the bundle tested in runs 6–8 is the stable 04:41–04:42
  rebuild, verified present and unchanged before the runs.
- No file outside `~/workspace/bootable-test/` was modified by this
  harness. All other directories were read-only; A/B files were only
  read and copied.
- No QEMU run was left running; every run ended by panic-exit,
  watchdog kill, or the loop timer. No push, no WorkBuddy, no credits
  were used by this task.
